## HIGH-1. ✅ ИСПРАВЛЕНО (3009d2e). Роли ANALYST и COORDINATOR видят и правят данные всех брокеров (broken access control)

**Где:** авторизация во всех CRM-роутах. Корень — паттерн «чёрного списка»:
```ts
const restrictedRoles = ['BROKER', 'REALTOR', 'AGENCY'];              // ~30 мест
const RESTRICTED_ROLES = ['BROKER', 'REALTOR', 'AGENCY', 'DEVELOPER']; // ещё ~10
if (restrictedRoles.includes(req.user.role) && obj.brokerId !== req.user.userId) {
  return res.status(403)...
}
```
Список перечисляет, кого **ограничить**. Любая роль, которой в списке нет, получает доступ ко всему. `COORDINATOR` и `ANALYST` добавлены в enum в этой сессии, но ни в один из ~40 списков не попали — и молча получили доступ ко всему контуру.

**Что подтверждено (PoC на локальном прод-образе, чистая база, три клиента у двух брокеров):**

| Роль | `GET /api/clients` | Что видит |
|---|---|---|
| BROKER-1 | 2 | только свои |
| ANALYST | 3 | **всех брокеров**, с ИИН: `[222…, 111…, 123…]` |
| COORDINATOR | 3 | **всех брокеров** |

- **Чтение:** `clients`, `buyers`, `sellers`, `deals`, `commissions`, `bookings` — по всем брокерам. В ответе — ИИН (нац. идентификатор РК), доход, телефон, email. Проверено также на живом проде под `analyst@casa.kz`.
- **Экспорт:** `GET /api/export/clients?format=csv` → HTTP 200, выгрузка ИИН/дохода/телефонов **всех** клиентов (в `where` для не-restricted ролей фильтр пустой).
- **Запись и удаление:** роуты `PUT/DELETE` у `buyers`, `sellers`, `deals`, `crm-properties`, `selections` **не** защищены `requireRole` — только той же проверкой по чёрному списку. `ANALYST` правит чужого покупателя: `PUT /api/buyers/:id` → **HTTP 200**, запись изменена.
  - Исключение: `clients` — там `PUT/DELETE` дополнительно закрыты `requireRole('BROKER','ADMIN')`, поэтому запись/удаление клиентов ANALYST/COORDINATOR недоступны. Чтение и экспорт клиентов — доступны.

**Почему High:** роль, задуманная как «read-only проверка оценок» (ANALYST) и «координатор сделок вторички» (COORDINATOR), фактически получила сквозной доступ к ПДн всех клиентов агентства и право менять/удалять чужие сделки и объекты. Требуется валидная внутренняя учётка (не аноним), но это настоящий broken access control, и паттерн — мина: **каждая новая роль по умолчанию получит полный доступ.**

**Как чинить (правильно — по образцу `deal-room.routes.ts`):** заменить чёрный список на белый. Ввести один модуль политики, например `lib/access.ts`:
```ts
// Кто видит ЧУЖИЕ записи основного CRM. Все остальные — только свои.
export const CRM_GLOBAL_READ = ['ADMIN'] as const;
export function scopeToOwner(role: string, userId: string) {
  return CRM_GLOBAL_READ.includes(role as any) ? {} : { brokerId: userId };
}
```
и решить продуктово, что вообще должны видеть ANALYST/COORDINATOR. **Реализовано:** решение — «весь CRM только чтение». Введён `lib/access.ts` с middleware `blockCrmWrites` (403 на любой не-GET от этих ролей), навешен на 13 бизнес-роутеров после `authenticate`; Deal Room и оценка не тронуты. Проверено на проде: чтение/экспорт 200, POST/PUT 403, вторичка для координатора 200.

## MEDIUM-2. ✅ ИСПРАВЛЕНО (3009d2e). Токен нельзя отозвать: деактивация и смена роли не действуют до истечения 7 дней

**Где:** `lib/jwt.ts`, `middleware/auth.middleware.ts`. JWT stateless, срок 7 дней, серверного списка отзыва нет.

- `logout` только чистит cookie на клиенте — сам токен остаётся валиден 7 дней.
- Если пользователя выключили (`isActive=false`) или понизили роль — **выданный токен продолжает работать**: `authenticate` проверяет только подпись, а `isActive`/`role` перечитываются лишь при новом логине.

**Последствие:** уволенный/заблокированный сотрудник или скомпрометированная учётка сохраняют полный доступ до недели. С учётом HIGH-1 это особенно неприятно для ANALYST/COORDINATOR.

**Реализовано (вариант а):** `authenticate` на каждом запросе читает `isActive`/`role` пользователя из БД; неактивный — 401, роль в `req.user` берётся из БД. Проверено: тем же токеном 200 → деактивация → 401.

## MEDIUM-3. ✅ ИСПРАВЛЕНО (7cd6769). httpOnly-cookie обнулён хранением токена в localStorage

**Где:** `auth.routes.ts` ставит `httpOnly + secure + sameSite` cookie **и** возвращает токен в теле; фронт (`components/login-form.tsx`, `lib/api-client.ts`) берёт токен из тела и кладёт в `localStorage`, оттуда шлёт `Authorization: Bearer`.

**Последствие:** защита httpOnly-cookie не работает — токен доступен из JS, то есть выгружаем любым XSS. Cookie висит «для галочки». Сейчас XSS-стоков не найдено (React экранирует, единственный `dangerouslySetInnerHTML` в CRM обёрнут в `DOMPurify.sanitize`), но при появлении любого XSS цена — сразу угон 7-дневного токена.

**Реализовано:** переход на cookie-only. Токен убран из тела ответа и из localStorage; сессия — в httpOnly-cookie `SameSite=None; Secure` (crm и API — разные сайты `*.up.railway.app`, иначе cookie не уходит). Фронт шлёт cookie через глобальный патч fetch (`lib/api-credentials`) и `withCredentials` у axios; роль читается из объекта `user`, logout зовёт `/auth/logout`.

**CSRF, который открывает SameSite=None, закрыт** новым `csrfGuard` (backend): изменяющие методы с чужого Origin → 403; запросы без Origin (curl, сервер-сервер) и GET проходят; Bearer-путь в `authenticate` сохранён для обратной совместимости. Добавлено 3 теста барьера.

Проверено в реальном браузере на проде под демо-брокером: cookie `httpOnly=true, sameSite=None, secure=true`, `localStorage.token=null`, экраны грузятся по cookie, `/auth/me`=200, logout гасит cookie (`/auth/me`=401). CSRF на проде: чужой Origin → 403, свой → проходит.

## Что проверено и оказалось в порядке (доказательно)

- **Зависимости:** `npm audit` во всех трёх приложениях — **0/0/0** (prod и с dev).
- **Заголовки прода:** helmet отдаёт CSP, HSTS (`max-age=31536000; includeSubDomains`), `x-content-type-options: nosniff`, `x-frame-options: SAMEORIGIN`, `referrer-policy: no-referrer`.
- **Инъекции:** raw-SQL нет нигде, кроме `SELECT 1` в healthcheck; всё через Prisma (параметризовано). SQLi нет.
- **SSRF:** единственный внешний вызов — DeepSeek по захардкоженному хосту, URL из пользователя не строится.
- **Mass assignment:** на большинстве роутов zod-схема (`.parse`) отсекает лишние поля; `brokerId` на create проставляется сервером из `req.user`. Подмена `brokerId` в теле при создании клиента проигнорирована (проверено).
- **IDOR:** между брокерами изоляция держится — `clients` (чтение и запись), `tasks`/`events`/`custom-funnels` (scoped по `userId`). Брокер-2 к объекту брокера-1: GET/PUT/DELETE → 403 (проверено).
- **Эскалация роли:** `PUT /api/auth/profile` с `role:ADMIN`/`balance:…` — проигнорировано, в БД роль и баланс не изменились (проверено). Админские роуты (`/admin/*`, `import`, `moderation`, `settings`, `search`, `subscriptions`, `payments`) отдают брокеру 403 (проверено). Агентство создаёт сотрудников с принудительной ролью `REALTOR`.
- **Rate limiting:** глобально 200/мин, логин 20/15 мин.
- **Пароли:** bcrypt(10), при логине общий текст ошибки (не раскрывает, есть ли email).

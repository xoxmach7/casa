# Шахматка ЖК + Фиксация клиента — дизайн

**Goal:** дать брокеру в CRM экран шахматки новостройки в духе Alemica — с переключателем видов (карточки / список / настоящая табличная шахматка по этажам и подъездам) и рабочей кнопкой «Фиксировать клиента», которая создаёт настоящую фиксацию в уже существующем бэкенде и выдаёт скачиваемый лист фиксации.

**Architecture:** фронтенд-переделка одной страницы (`/dashboard/projects/[id]/apartments`) поверх уже готового бэкенда (`Fixation`/`FixationStatusLog`, `fixations.routes.ts` с рабочей стейт-машиной). Бэкенд-изменения: новая модель `Building` + поле `entrance` на `Apartment` (сейчас в базе вообще нет понятия «здание/подъезд» — один Проект = плоский список квартир), два новых поля на `Fixation`, и правка TTL с 14 дней на 24 часа. PDF генерируется на клиенте, новый эндпоинт под него не нужен.

**Tech Stack:** Next.js/React (существующий CRM), Prisma/Postgres, `jspdf`+`jspdf-autotable` (уже в зависимостях фронтенда).

---

## Контекст и референс

Пользователь показал скриншоты продукта Alemica (alemica.com) — базу объектов новостроек со сплит-view шахматкой, кнопку «Фиксировать клиента», и реальный PDF «Лист фиксации» от BI Group (формат: Партнёр / Клиент / Интерес клиента / Специалист застройщика).

В нашем бэкенде уже есть **полностью рабочая** модель `Fixation` со стейт-машиной (`DRAFT → SENT → CONFIRMED → BOOKING_REQUESTED → BOOKED → DEAL`, плюс отказы/истечение), но **никакого UI под неё никогда не было построено** — это чистый бэкенд-сирота. Также есть `/dashboard/projects/[id]/apartments` — простая сетка квартир по этажам с диалогом деталей и кнопкой «Забронировать» (ведёт в отдельный `Booking`-флоу).

## Явно вне скоупа (решено в диалоге, не переспрашивать)

- Кнопка «Проверить клиента» (анти-перекуп проверка дублей) — не делаем.
- SMS-подтверждение клиента — в проекте нет SMS-провайдера, это отдельная задача на будущее.
- «Проверить ИИН» и блок одобрения ипотеки от банков (как в референсе) — отдельные крупные фичи, не запрошены.
- Отслеживание оплаты («Оплачено» как шаг стейт-машины) — в базе нет поля под это, не выдумываем.

## Что меняется

### 0. Новые сущности: здание и подъезд

Сейчас `Apartment` привязан только к `Project` — ни зданий («Arena City Life - C»), ни подъездов («Подъезд 1») в базе нет. Добавляется:

```prisma
model Building {
  id         String      @id @default(cuid())
  name       String      // "Arena City Life - C", "Блок B" и т.п.
  projectId  String      @map("project_id")
  project    Project     @relation(fields: [projectId], references: [id], onDelete: Cascade)
  apartments Apartment[]
  createdAt  DateTime    @default(now()) @map("created_at")

  @@index([projectId])
  @@map("buildings")
}
```

На `Apartment`: `buildingId String? @map("building_id")` (relation на `Building`) + `entrance Int? @map("entrance")`. Оба **опциональные** — существующие квартиры без здания/подъезда не ломаются, просто не участвуют в группировке (попадают в вид «без здания», карточки/список продолжают показывать их как раньше). Управление зданиями — простое инлайн quick-create в форме добавления/редактирования квартиры (`/dashboard/projects/[id]/apartments/new` и `/edit`), без отдельной страницы управления зданиями — по образцу quick-add у покупателя в `InterestTab.tsx`.

Позиция квартиры **в колонке** шахматки (какая колонка на каком этаже) — не отдельное поле, а производится сортировкой: внутри одного здания+подъезда+этажа квартиры сортируются по `number`, порядковый номер = номер колонки. Работает, только если на каждом этаже одинаковое количество квартир (обычная практика для типовых секций) — если нет, колонки этой секции просто съезжают начиная с этажа, где квартир меньше; это ограничение, а не баг, отдельное поле «позиция на этаже» не заводим, пока не понадобится.

### 1. Шахматка — три вида + переключатель

`/dashboard/projects/[id]/apartments` получает переключатель видов (3 иконки, как на референсе):

- **Карточки** — примерно как на текущей странице сейчас (сетка карточек по этажам), минимально причёсанная.
- **Список** — сплит-панель: список юнитов слева (номер, комнатность, площадь, статус/цена, бейдж класса если у `Project.class` есть значение), детали справа.
- **Шахматка (таблица)** — настоящая табличная сетка: если у проекта есть здания — селектор здания, затем селектор подъезда; строки — этажи (сверху вниз, по убыванию), колонки — позиция на этаже (см. §0). Ячейка — компактная карточка (номер, комнатность, площадь, цена/статус), цвет по статусу, замо́к на занятых. Клик по ячейке = то же самое выделение юнита, что и в виде «Список» — общая деталь-панель справа переиспользуется всеми тремя видами через один и тот же state.

Все три вида ведут в одну и ту же панель деталей юнита (фото планировки если есть, характеристики, способ оплаты + сумма, кнопка «Фиксировать клиента») и одни и те же фильтры (комнаты/статус/этаж) в шапке.

Кнопка **«Забронировать» убирается из этого экрана** — её роль полностью берёт на себя «Фиксировать клиента». Модель `Booking` и её роуты не удаляются (могут использоваться где-то ещё/понадобиться позже), просто эта конкретная точка входа исчезает.

### 2. Модалка «Фиксировать клиента»

Поля:
- Фамилия, Имя (обязательно)
- Телефон (обязательно) — при вводе ищем существующего `Client` по телефону (`GET /clients?search=<phone>`); если есть — переиспользуем, если нет — создаём.
- Способ оплаты — **фиксированный выбор**: `100%` / `Ипотека` / `Рассрочка` (не свободный текст).
- Сумма ДДУ — по умолчанию цена квартиры, с возможностью поправить (сделка не всегда точно по прайсу).

**Клиент без ИИН:** `createClientSchema` на бэкенде требует ИИН (12 цифр) — на референсе же клиент на этапе фиксации часто «Неизвестный», без документа. Решение по прецеденту из `import.service.ts` (там для CSV-импорта без ИИН уже генерируется плейсхолдер `IMPORT-${rowNumber}`): при создании клиента из фиксации без указанного ИИН ставим плейсхолдер `FX-<timestamp>`, донабрать реальный ИИН можно позже через обычную карточку клиента.

По сабмиту: (1) найти-или-создать `Client`, (2) `POST /fixations` (create as DRAFT) с новыми полями способа оплаты/суммы, (3) сразу `PATCH /fixations/:id/status {status: SENT}` — с точки зрения брокера это одно действие «отправить», а не два отдельных шага.

### 3. Fixation-карточка после создания

Показывает: № фиксации, статус, дедлайн истечения (`expiresAt`, теперь 24 часа вместо 14 дней), упрощённый степпер по **реально существующим** статусам (Отправлено → Подтверждено → Бронь → Сделка — берём подмножество `FixationStatus`, не весь список), кнопку «Скачать PDF».

### 4. Лист фиксации (PDF)

Генерируется на клиенте через `jspdf`/`jspdf-autotable` (уже есть в зависимостях, используются для других экспортов — новых npm-пакетов не требуется). Структура — как в референсе BI Group, адаптированная под CASA:

- Партнёр: агентство «CASA Pro», ФИО и телефон брокера (текущий пользователь), дата.
- Клиент: ФИО, телефон.
- Интерес клиента: ЖК, Квартира, Способ оплаты, Сумма ДДУ.
- Специалист застройщика — блок оставлен пустым (Отдел продаж / Хантер / Дата приёма / Подпись / Комментарий), как в референсе — это поле для внутреннего использования застройщиком, не наша ответственность.
- Срок действия — 24 часа от отправки, отражается на самом листе.

## Бэкенд-изменения (аддитивные, без удаления существующего)

**Миграция 1** — новая модель `Building` (см. §0) + на `Apartment`: `buildingId String?`, `entrance Int?`.

**Миграция 2** — на `Fixation` добавляются:
- `paymentMethod FixationPaymentMethod?` — новый enum `FULL | MORTGAGE | INSTALLMENT`.
- `dealAmount Decimal? @db.Decimal(15, 2)` — сумма ДДУ.

**`apartments.routes.ts` / `projects.routes.ts`:** нужен способ создать `Building` (скорее всего `POST /projects/:id/buildings`, простой CRUD без стейт-машины) и принять `buildingId`/`entrance` при создании/редактировании квартиры. `GET /apartments` должен отдавать `building`/`entrance` в ответе, чтобы фронт мог группировать.

**`fixations.routes.ts`:**
- `createFixationSchema` расширяется полями `paymentMethod`/`dealAmount` (опционально на создание, но UI всегда будет их слать).
- TTL при переходе в `SENT`: `14 * 24 * 60 * 60 * 1000` → `24 * 60 * 60 * 1000` (24 часа вместо 14 дней) — это правка уже живой продовой логики, не новой.

PDF — на клиенте, новый роут не нужен. Поиск клиента — через уже существующий `GET /clients?search=`.

## Что НЕ трогаем

- `/dashboard/projects` (список ЖК) — остаётся как есть, редизайну не подвергается.
- Booking-модель и её роуты — не удаляются, просто не вызываются с этого экрана.
- Остальные статусы `FixationStatus` (`DUPLICATE_CHECK`, `REJECTED_*`, `EXPIRED`, `CANCELLED`) — остаются в схеме и бэкенде нетронутыми, просто в MVP-степпере не визуализируются все (только основной happy-path).

## Тестирование

- Backend: юнит-тесты на новый TTL (24ч), на приём `paymentMethod`/`dealAmount` в create-роуте, на CRUD зданий и на то, что `GET /apartments` отдаёт `building`/`entrance`.
- Frontend: ручная проверка в браузере (dev-сервер) — переключение между тремя видами на проекте с несколькими зданиями и на проекте без них (старые данные, `buildingId`/`entrance` пустые — виды не должны падать), выбор юнита → фиксация → скачивание PDF, сценарий «клиент уже есть в базе по телефону» и «клиента нет — создаётся с плейсхолдер-ИИН».

# CASA Pro Mortgage Production Sandbox Design

## Goal

Restore the authenticated CASA Pro mortgage workspace in production as a clearly labelled sandbox that exercises the real deterministic mortgage core without enabling legacy public demo endpoints or accepting real personal data.

## User flow

1. An authenticated CASA employee opens `/dashboard/mortgage`.
2. The page clearly states that this is a sandbox and only synthetic or anonymized documents are allowed.
3. “Заполнить демо” loads the complete synthetic case locally and remains available even if document upload is not used.
4. The employee may upload text-layer PDF samples for credit history and ENPF.
5. The backend rejects scans without an extractable text layer, files containing a valid Kazakhstan IIN, unsupported MIME/magic bytes, or oversized files before persistence.
6. Accepted files are stored in the existing private persistent mortgage directory, owned by the authenticated user, and never exposed through static `/uploads` routing.
7. Extracted fields are shown for mandatory manual review. Confirmation stays owner/admin scoped.
8. Analysis and scenario responses are produced through `runMortgagePreScore` and `previewMortgageScenario`; the UI must not label local mock calculations as server results.
9. Public consent/SMS and public conclusion links remain unavailable in production sandbox. The UI shows an explicit “requires provider/legal integration” state instead of creating a fake public link.

## Backend contract

The existing authenticated `/api/mortgage-workspace` namespace becomes a sandbox-only adapter. It is no longer controlled by the broad `ENABLE_DEMO_ENDPOINTS` switch. Public `/api/public/mortgage` endpoints remain fail-closed in production.

Endpoints used by the workspace:

- `GET /sandbox/status` — returns enabled mode, constraints, and supported document types.
- `POST /documents` — validates PDF bytes and synthetic-data policy, extracts fields, then persists privately.
- `GET /documents/:id` and `GET /documents/:id/file` — owner/admin only.
- `PATCH /documents/:id/confirm` — owner/admin only; rejects unresolved critical fields.
- `GET /sandbox/analysis` — deterministic synthetic reference analysis generated by the real Pre-Score core.
- `POST /sandbox/scenarios` — validates and evaluates a scenario through the real scenario core.

No endpoint accepts a client-provided claim that can bypass synthetic-data inspection. There is no in-memory consent token, fake SMS, fake government check, or production public conclusion.

## Synthetic-document policy

- PDF content type and `%PDF-` magic bytes are both required.
- Maximum size remains 25 MiB.
- A usable text layer is required; OCR is outside this increment.
- A valid Kazakhstan IIN detected in extracted text causes rejection before file persistence.
- The request includes a visible user attestation that the file is synthetic/anonymized; the server requires it but does not rely on it as the only control.
- Saved metadata records sandbox mode, uploader, checksum, policy version, and extraction outcome. Logs contain identifiers and hashes only, not extracted text or document bodies.

## Frontend changes

- Replace the misleading “server unavailable → demo fields” fallback with truthful error handling.
- Add a permanent sandbox banner and explicit file-policy acknowledgement.
- Keep one-click synthetic demo completion, but label all synthetic values.
- Fetch sandbox status before enabling upload.
- Use server-returned analysis/scenarios; do not silently substitute mock results after an HTTP error.
- Disable public-link generation and IIN verification claims, with clear provider-gate explanations.

## Verification

- Backend unit/route tests reproduce the current production 404 and prove the authenticated sandbox route is available while public demo routes remain disabled.
- Upload tests cover PDF magic bytes, valid-IIN rejection, unreadable scans, ownership, persistence, and successful synthetic extraction.
- Core adapter tests prove analysis/scenarios call deterministic services and remain fail-closed for invalid input.
- Frontend tests cover the sandbox banner, status loading, successful upload, truthful failures, and absence of fake public-link/IIN success.
- Full backend/frontend tests, typecheck, builds, Prisma validation, Playwright mortgage smoke, CI, deploy, and production smoke are required before completion.

## Follow-up: complete production mortgage core

The sandbox does not pretend to provide real credit-bureau, ENPF, government, SMS, bank, KMS, malware-scanning, or legal-retention capabilities. The next release must connect the already implemented case/consent/document/snapshot/rule/scenario models to named production providers and approved policies, then expose real-client workflows only after those gates are satisfied.
